## Reading it

A miss is one expert (~2 MB on this file) over PCIe, read in place; a fill is a second
transfer of the same bytes (the copy into the slot). PCIe transfers per 100 picks = read +
fills (320 picks per step: 40 layers x 8):

| policy (pinned share) | code | ita | tech | wiki |
|---|---:|---:|---:|---:|
| today: 32 slots per layer, 2nd-miss admission (40 %) | 8.36 | 3.07 | 4.43 | 12.93 |
| 32 slots shared per layout, 2nd-miss admission (40 %) | 7.92 | 2.41 | 3.96 | 12.44 |
| 32 slots shared, 1st-miss admission, fill counted (40 %) | 10.70 | 2.74 | 4.66 | 19.48 |
| 32 slots shared, 1st-miss admission, fill = the read (40 %) | 5.35 | 1.37 | 2.33 | 9.74 |
| 64 slots shared, 2nd-miss admission (53 %) | 6.75 | 2.45 | 3.92 | 8.02 |
| llama.cpp's shape: all slots shared, 1st-miss upload (100 %) | 2.60 | 1.05 | 1.96 | 2.26 |

The scale in time: #512 step 3 moved code from 7.61 % to 4.24 % read (both with their fills)
and the step from 14.43 to 12.33 ms, ~0.6 ms per point of host reads on this machine.

1. Sharing the LRU slots across the layers of a layout (llama.cpp's grouping), same RAM:
   -0.4..-0.7 transfers per 100 picks, ~0.2-0.4 ms per step (2-3 %).
2. llama.cpp's admission (every miss enters) only pays when the fill is not a second
   transfer: llama.cpp computes from the uploaded copy (a host sync per layer). The
   omphalos-native equivalent is a fill written by the expert kernel itself while it reads
   the miss (the victim slot chosen ahead, on the device): -36 % / -55 % / -47 % / -25 % of
   the transfers at the same RAM, ~1-2 ms per step on code by the scale above.
3. More pinned RAM buys the rest (wiki 12.9 -> 8.0 at 53 %, 2.3 at 100 %): a RAM decision
   (#512 chose ~7.8 GB).
