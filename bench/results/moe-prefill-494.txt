# The MoE prefill of the second model: the batched path (#494)

Model: Ornith-1.5-35B-A3B-Q2_K_L.omph (12.65 GiB, VRAM-resident). Prompt: a
repeated sentence (2001 tokens), one to four 512-token chunks. Same machine,
desktop active, one run per point (the prefill is per-chunk deterministic and
the numbers vary by <1 % across runs).

The v1 (per-token loop, #493) is ~77 ms per token = ~13 t/s of prefill; the
batched path is what this measures.

| tokens | chunks | prefill wall | t/s |
|---:|---:|---:|---:|
| 512 | 1 | 1332.4 ms | 384 |
| 1024 | 2 | 2522.9 ms | 406 |
| 2000 | 4 | 4630.3 ms | 432 |

`OMPH_PHASES=1` for one 512-token chunk:

```
phases: stage_w 74.9 ms  gemm(f16) 608.8 ms  gemv 0.0 ms  blocks 123.8 ms
        | calls 2490/15435/0/40
prefill wall 1335.9 ms (512 tokens)
```

The f16 GEMMs are 46 % of the chunk: the 256 experts of every layer are 256
small GEMMs (M=512 / 2048, N~16, K=2048 / 512) with a launch each - ~30k
launches per chunk. The grouped expert GEMM (one grid over expert x tile) is
the next step; the achieved weight bandwidth is ~14 GB/s against the ~400 GB/s
the card has, so this is grid/launch bound, not bandwidth bound.

## Correctness

- the batched path gives the same logits as the per-token one: KL 0.004501
  nats vs llama.cpp's CPU dump, top-1 100 % (the same as `qwen35moe-493.txt`)
- **chunk-invariant**: a 512-token prompt with `--chunk 512` and with
  `--chunk 128` is bit-identical (KL 0.000000 nats, top-1 100 %): the per-slot
  store plus the slot-ordered combine make the expert sums independent of the
  chunking (no atomics)

## The grouped expert GEMM (the same chunk, one launch per matrix kind)

`gemm_q_grouped` (the tile kernels with an expert grid dimension: `blockIdx.z`
picks the expert, its weight slice and its rows of x) replaces the per-expert
GEMMs; the fallback stays for the types without a tile kernel (this file's Q3_K
down projections, half of them) and for the A/B (`OMPH_MOE_NO_GROUP=1`):

| tokens | per-expert GEMMs | grouped | grouped t/s |
|---:|---:|---:|---:|
| 512 | 1373.6 ms | 811.7 ms | **631** |
| 1024 | - | 1876.3 ms | 546 |
| 2000 | - | 3754.8 ms | 533 |

Same logits either way (KL 0.004501 vs llama.cpp, top-1 100 %) and still
chunk-invariant (KL 0.000000). The remaining time is the per-layer ids readback
and the Q3_K down projections through the f16 staging path (#492 step 2).

The launch count per layer went from ~256 x 5 to ~6; the achieved weight
bandwidth from ~14 GB/s to ~31 GB/s (the whole expert set per layer, 464 MiB,
over ~15 ms). llama.cpp's own numbers on this machine: 959 t/s at 512 tokens
(Q4_K_M, 25 layers' experts on GPU) and 651 t/s at 128k depth.

## The router as a GEMM, and the deep-context target (#494, #490)

`rocprofv3` said the router was 57 % of the prefill: `moe_route` computed the
256 expert logits per token with a per-thread *scalar* f32 dot (16.7 ms per
layer for a 1024-token chunk, ~32 GFLOP/s). The router weights are converted to
f16 once at load (1 MiB per layer, 40 MiB) and the logits are a plain f16 GEMM
(the engine's WMMA `gemm_f16`); `moe_topk` then does the softmax and the top-k on
the logits. The end-to-end KL *improved* slightly (0.004501 -> 0.004359: the
f16 GEMM's accumulation is better than the scalar dot's against the f16 x).

| tokens | before | after | t/s |
|---:|---:|---:|---:|
| 512 (chunk 512) | 811.7 ms | 341.1 ms | **1501** |
| 4096 (chunk 1024) | 4463.3 ms | 1835.0 ms | **2232** |

The #490 target at the depths the maintainer asked for (Q2_K_L, VRAM-resident):

| depth | omphalos | llama.cpp | ratio |
|---|---:|---:|---:|
| 128k | **93.1 s** (1408 t/s) | 201 s (651 t/s) | 2.16x |
| 160k | **127.3 s** (1287 t/s) | 272 s (603 t/s) | 2.14x |

Both are inside the acceptance bar (128k in <= 2 min, 160k in <= 3 min) with the
Q2_K_L; the same file llama.cpp ran for those anchors is the Q4_K_M, so the fair
A/B is still #495's placement. Chunk invariance still holds (KL 0.000000 with
`--chunk 512` against `--chunk 256`).

Remaining in the profile at 8k/1024: the delta-net's token-sequential path
(14 %: the work buffer's `ffn_n_` proxy usually does not let it take the
token-parallel form), the Q3_K down projections through the f16 staging path
(7 %, #492 step 2), the store kernel (3 %) and the attention (1.3 %).
