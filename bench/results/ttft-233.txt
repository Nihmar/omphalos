# Time to first token through the servers (#233) — partial, see "state"

Engine a010be4 (the campaign tree), RX 9060 XT 16 GB, CachyOS, desktop session
active. A wikitext prompt of the target size in a chat template (rendered once
with omph-tokenize, the same text to both engines), streamed, one token to
generate, prompt caching off (`--cache-ram 0 --kv-ram 0` on omphalos,
`cache_prompt: false` on llama.cpp), median of 5 runs after one warm-up
(tools/ttft.py, PLAN.md §17). TTFT is the first streamed delta: template +
tokenization + HTTP + prefill; the "overhead" column is TTFT minus the server's
own `timings.prompt_ms`.

* llama k4q4 100k has 2 of the 5 runs; the parse is recomputed from the JSONLs.
The omphalos rows are complete for all three cache settings (k4q4 = `OMPH_KV_K4=1`,
k8q4 = the default mix, k8 = `OMPH_KV_K4_LAYERS=none`); k4q4 and k8 are within
1 % of each other at every size (the prefill reads the FP16 window regardless
of the quantization), so the cache precision is not a TTFT knob.

Reading so far: omphalos' prefill is 1.6-2.0x llama.cpp's at every size
(1042 vs 553 t/s at 500, 682 vs 419 t/s at 100k), and the server overhead
(tokenization + template + HTTP) is 1-2 ms at 500 and ≤ 132 ms at 100k on both.
The 100k TTFT at ~147 s is the number a user actually waits for; at 32k it is
36 s.
