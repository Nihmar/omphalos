# Q8_0 / Q4_0 / Q5_K GEMVs with k split across the workgroup's warps (#563, step 1)

engine: main d3b8f2a vs perf/563-legacy-ksplit; RX 9060 XT 16 GB, desktop active.

## Kernel time (rocprofv3, Ornith Q4_K_M, 128 greedy tokens, per decode step)

| | main | k split | k split + vector loads (tried, dropped) |
|---|---:|---:|---:|
| legacy + Q5_K GEMVs | 1.57 ms | 1.42 ms | 1.49 ms |
| gemv_legacy32<Q8, 1> | 0.879 ms (16.3 us avg) | 0.774 ms (14.3 us) | 0.750 ms (13.9 us) |
| gemv_q5k<1> | 0.342 ms (34.2 us) | 0.333 ms (33.3 us) | 0.422 ms (42.2 us) |
| gemv_legacy32_gu<Q8> | 0.351 ms (17.6 us) | 0.309 ms (15.5 us) | 0.323 ms (16.2 us) |

Four times the workgroups barely moved Q5_K (34.2 -> 33.3 us): these bodies are bound by their
per-byte loads and scalar dequant, not by parallelism; 16-byte loads of x and of the Q5_K bytes
cost registers and lost (Q5_K 42.2 us). A WMMA tile layout for these types (#563 step 2) is what
would bring them near the bandwidth bound (~0.9 ms per step for the same tensors).
