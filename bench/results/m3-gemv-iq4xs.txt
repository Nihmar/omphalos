# M3.2 — fused IQ4_XS GEMV + repacking (2026-09-30)

Type IQ4_XS: 4-bit codes into the 16-entry non-linear codebook `kvalues_iq4nl`,
per-sub-block `d * (scale6 - 32)`. 2.81 GiB of the allocation, 96 tensors — the
second-largest type after IQ3_S.

Conditions: `omph-gemv-bench`, median of 5 runs, ROCm 7.2.4, gfx1200, desktop
idle (PLAN.md §17). Ceiling: 318.3 GB/s measured (`bench/results/m0-bandwidth.csv`).

## Summary (median of 5 runs)

| measurement | time | bytes read | effective bandwidth | vs ceiling |
|---|---:|---:|---:|---:|
| all 96 IQ4_XS tensors, one pass | **11.72 ms** | 2924.4 MiB | **261.6 GB/s** | **82.2 %** |
| single tensor `blk.63.ffn_up` (45.2 MiB) | 0.165 ms | 45.8 MiB | 291.5 GB/s | 91.6 % |
| *(reference: Q4_K `output.weight`, M3.1)* | 2.90 ms | 701.0 MiB | 253.2 GB/s | 79.6 % |

Repacking verified lossless for all 96 tensors (rebuild of the source block
stream compared byte for byte). Accuracy against the f16 dequant + hipBLASLt
path: max |d| 7e-4 (2.4e-4 relative), mean |d| 1e-4.

## Optimisation attempts (measured)

Final state: **261.6 GB/s = 82.2 % of the ceiling** over the whole type (169.1 before).

| change | result | kept? |
|---|---:|---|
| baseline | 169.1 GB/s (53.1 %) | — |
| activation staging in chunks of 256 sub-blocks (16 KiB LDS) | 186.0 GB/s (58.4 %) | yes |
| **outer product: 4 output rows per warp** (one activation value feeds four rows, four independent FMA chains) | **261.6 GB/s (82.2 %)** | **yes** |
| rows per warp = 2 | 183.1 GB/s (57.5 %) | no |
| rows per warp = 8 | 146.7 GB/s (46.1 %) | no |
| activation read as `__half2` | 80.8 GB/s (25.4 %) | no |
| activation read as `uint4` | 82.3 GB/s (25.9 %) | no |
| padded LDS stride (34 halves, coprime with the banks) | 126.0 GB/s (39.6 %) | no |
| *diagnostic:* codebook lookup replaced by an arithmetic placeholder | 201.9 GB/s (63.4 %) at baseline | n/a |

Reading of the evidence: the kernel was **instruction-issue/latency bound**, not
LDS-conflict bound — the padded layout (which removes the 16-way conflict) made
things *worse*, while amortising one activation load over four rows and adding FMA
independence made them 40 % better. The surviving ideas are the ones that reduce
instructions per weight, not the ones that change the access pattern.

| change | result | kept? |
|---|---:|---|
| baseline | 169.1 GB/s (53.1 %) | — |
| **activation staging in chunks of 256 sub-blocks** (16 KiB LDS) instead of the whole k | **186.0 GB/s (58.4 %)** | **yes** |
| activation read as `__half2` (16 LDS ops per 16 weight bytes instead of 32) | 80.8 GB/s (25.4 %) | no |
| activation read as `uint4` + chunked staging | 82.3 GB/s (25.9 %) | no |
| *diagnostic:* codebook lookup replaced by an arithmetic placeholder (wrong values, same loads) | 201.9 GB/s (63.4 %) | n/a |

The chunked staging is kept: with it, the k = 17408 tensors stage 16 KiB instead of
34 KiB of LDS, which lifts the workgroup-per-CU limit. It is worth +10 % over the
whole type.

Both attempts to read the activation with vector loads made things **2x worse**, and
the reason is not yet understood — 32 lanes stepping one 64-byte sub-block each means
the LDS addresses are 64 B apart, i.e. every lane lands on the same couple of banks
(16-way conflict), and a wider load apparently serialises harder instead of helping.
The obvious follow-up is a padded/transposed LDS layout for the activation
(sub-block stride 33 halves instead of 32) so that consecutive lanes hit consecutive
banks, and re-testing the vectorised reads on top of that.

## Why it is slower than Q4_K

The core loop is the same shape, but every value needs a **codebook lookup with
a divergent index**, which lands in LDS. Two measurements narrow it down:

- Factoring the per-sub-block scale out of the sum (`acc += dl * Σ table[c]·x`
  instead of `Σ (dl·table[c])·x`) and switching the LDS table from int8 to f32
  changed the result by 0.2 % (52.8 -> 53.0 %), so the kernel is **not ALU-bound**.
- The aggregate (2.9 GiB) and the single 45 MiB tensor agree within 2 %, so it
  is not L2 residency or launch overhead either.

That points at the LDS/bank behaviour of the 16-entry lookup (32 divergent
lookups per 16 bytes read). Follow-ups to try, in order:

1. Select the codebook entry with byte-permute instructions (`v_perm_b32` over
   four 32-bit registers holding the 16 int8 values) instead of an LDS gather.
2. Keep the codes' low/high nibbles in separate streams so each lane's 16-byte
   load covers one 32-value run of a *single* sub-block (better locality).

# M3.6 — profiling attempt: occupancy, and why the HW counters are empty

## Hardware performance counters: not available

`rocprofv3 --pmc ...` runs and produces a counter CSV, but every value is 0
(the dispatch rows are there, the values are not) — the counters need the AMD
perf permissions this box does not grant, so no counter-based analysis is
possible without a sysctl change. What the CSV *does* give for free is the
static per-kernel resource usage:

| kernel | VGPRs | LDS (dynamic) |
|---|---:|---:|
| `gemv_q4k` (Q4_K) | 128 | k x 2 B |
| `gemv_iq4` (IQ4_XS) | 120 | 16.4 KiB |
| `gemv_iq3` (IQ3_XXS) | 120 | 17.5 KiB |
| `gemv_iq3s` (IQ3_S) | 152 | 18.4 KiB |

## Occupancy (hipOccupancyMaxActiveBlocksPerMultiprocessor, 256 threads)

`OMPH_OCCUPANCY=1 omph-gemv-bench ...` reports workgroups per CU: q4k 6,
iq4 3, iq3xxs 3, iq3s 3 with the *maximum* chunk reserved. 

That exposed a real waste: the wrappers asked for the largest chunk even when
k is small enough to fit in one (k = 5120 needs 10 KiB, not 16.4). The dynamic
LDS size is now `min(n_sub, chunk) * 64 + tables`, which raises the occupancy
for the common shapes. Measured effect on the aggregates so far: neutral
(261.2 vs 261.6 GB/s for IQ4_XS) — the big-k tensors were already chunked,
and the small-k ones were not occupancy-limited.

## Where this leaves the optimisation work

The counter data is unavailable, but the A/B experiments already measured the
answer for IQ4_XS: removing bank conflicts (padded LDS) made things *worse*,
while removing instructions per weight (outer product over 4 rows) made them
40 % better. So the kernels are instruction/latency bound, not memory bound,
and the remaining levers are:

1. **Submission overhead** — the type aggregates lose 10-15 points on the
   small tensors (attn_k/attn_v are 2.7 MiB and run at 148 GB/s). HIP graphs
   are the fix, and they belong to M4.
2. **Small batch N = 1...5** — same weights, more tokens; the only lever that
   increases arithmetic intensity in decode (and it is what MTP verification
   needs).
3. **Wire the GEMVs into the runtime** — end-to-end decode numbers instead of
   per-tensor ones.

# M3.7 — fused GEMVs wired into the runtime (decode)

`--gemv` makes the runtime repack every tensor with a fused kernel at load and
use the GEMV for single-token steps; the rest falls back to the f16 dequant +
hipBLASLt path. Weights are read once and kept in one image (~11.4 GiB); the f16
fallback for repacked tensors re-stages the original bytes from the mmap.

## Decode (10-token prompt, 20 greedy steps timed)

| path | prefill | decode |
|---|---:|---:|
| f16 (milestone 2) | 2161 ms | **831 ms/token** (1.2 t/s) |
| **fused GEMV** | 8129 ms | **174 ms/token** (5.7 t/s) |

**4.8x faster decode, and the generated tokens are byte-identical to the f16
path** (198 760 3841 13477 37550 33075 888 279 15217 5388 13 198), which is also
the milestone-2 reference sequence.

Prefill got *slower* with `--gemv` (2161 -> 8129 ms): the f16 fallback for
repacked tensors stages the original quantized bytes from the mmap through the
host on every layer, ~1.6 GB per pass. Prefill speed is priority 3 and the M8
WMMA path replaces it; recorded rather than papered over.

## Where the remaining decode time goes

The covered 9.82 GiB should take ~39 ms at ~250 GB/s, so most of the 174 ms per
token is the **f16 fallback for the 1.46 GiB of uncovered types** (IQ2_S, Q6_K,
IQ2_XS/XXS, BF16/F32/IQ1_M = 14 % of the weights), which is read at 2 bytes per
weight instead of ~0.5 plus its dequant and staging. The next lever is therefore
not a faster kernel, it is **removing the fallback**: a GEMV for Q6_K and IQ2_S
covers most of it.

# M3.8 — fused Q6_K GEMV (0.32 GiB, but MTP-only)

| measurement | result |
|---|---:|
| all 8 Q6_K tensors (218.3 MiB) | **157.3 GB/s = 49.4 %** of the ceiling |
| accuracy vs the f16 dequant path | max \|d\| 6e-4 (**6.4e-5 relative** — the best of the five) |
| repack round-trip | byte-identical, source size (332.2 MiB) |
| rows per warp 2 / 4 / 8 | 142.9 / **157.3** / 79.5 GB/s |

The slowest kernel of the set. Each 128-weight group needs 96 quant bytes
extracted through two levels of shifts (16 `ql` words + 8 `qh` words held in
registers) plus a 4-quarter sub-accumulation, so it is heavier per value than
Q4_K/IQ4_XS and the register count shows it.

**Finding that matters more than the number: every Q6_K tensor in this model
lives in `blk.64.*`, the MTP block.** The normal decode path never touches them,
so this kernel is an M6 (MTP) enabler, not a decode win — and it does *not* help
the f16 fallback that dominates the current 174 ms/token.

That also corrects the previous estimate of the fallback: of the 1.46 GiB of
uncovered types, ~0.75 GiB is the token embedding (a row gather, not a GEMV) and
0.32 GiB is MTP. The fallback actually on the decode path is roughly 0.7 GiB
(6 % of the weights): IQ2_S outside the embedding, IQ2_XS/XXS and IQ1_M.

# M3.11 — the two questions: grid residency, and the cost of the sign

## (a) Does the grid's LDS residency matter?

No. Moving the IQ2_S grid (8 KiB) out of LDS into a const table (L1-resident,
freeing the LDS for occupancy) changed the kernel by 140.5 -> 139.6 GB/s, i.e.
nothing. So the kernel is not occupancy- or LDS-bound, and shrinking the grid's
footprint is not a lever.

## (b) Can the per-value sign select fold into the grid lookup?

The sign is *expensive* (removing it as a diagnostic — wrong results, valid
timing — gives 140.5 -> 189.1 GB/s, so it is worth ~26 % of the kernel), but it
does **not** fold away:

- it is a per-value mask (8 bits per 8-value group), not a per-group scalar, so
  it cannot go into the scale;
- folding it into the activation is impossible: the activation is shared by the
  four rows of a warp while each row has its own mask;
- the alternatives (pre-negated grid copies, `copysign`, ±1 tables, per-byte
  XOR masks) all cost at least the one op they would replace.

What *did* pay is the same class of win next to it: the byte extraction. The
compiler was emitting shift+mask+convert — three instructions per value — for
what the ISA does in one. `v_cvt_f32_ubyteN` is not exposed as a builtin for
gfx1200, so it goes through inline asm, built explicitly into float arrays (a
switch helper folded badly and cost 40 % everywhere).

| type | before | after |
|---|---:|---:|
| IQ2_S | 140.5 GB/s (44.1 %) | **233.6 GB/s (73.4 %)** |
| IQ2_XXS | 171.0 GB/s (53.7 %) | **231.2 GB/s (72.7 %)** |
| IQ2_XS | 166.1 GB/s (52.2 %) | **200.1 GB/s (62.9 %)** |
| IQ3_S | 219.5 GB/s (68.9 %) | 220.6 GB/s (69.3 %) |
| IQ3_XXS | 246.1 GB/s (77.3 %) | *reverted* — the array form cost 4 % there |

Accuracy is unchanged in every case (2.0-2.4e-4 relative).

End to end the decode stays at ~128 ms/token: those three types are only ~6 % of
the weights, so a 20-66 % kernel gain is worth ~4 ms. The value here is that the
slowest kernels are no longer an outlier — IQ2_XXS/S now sit with IQ4_XS and
IQ3_XXS — and that the same instruction replaces the extraction in any future
grid kernel.

# M3.12 — prefill phase breakdown (OMPH_TIMING=1)

10-token pass, f16 path, 2.0 s wall clock of which ~0.56 s is the one-time
weight upload over PCIe; the pass itself is ~1.45 s (~7 t/s).

| phase | time | share |
|---|---:|---:|
| dequant each layer's weights to f16 (`stage_w`) | 830 ms | 57 % |
| f16 GEMMs (hipBLASLt) | 339 ms | 23 % |
| attention / gated delta net kernels | 43 ms | 3 % |
| small ops, casts, launches (residual) | ~200 ms | 14 % |

Two conclusions for milestone 8:

- **80 % of the pass is the two things M8 replaces** (f16 materialization and
  small-M GEMMs), which is the quantitative version of the §4.2 argument.
- the block kernels are only 3 % *at T = 10* because the delta net is
  sequential today; they are exactly what grows with T, so the chunked form
  (§10.3) is what keeps a 512-token prompt from being delta-net bound.

Also fixed while measuring: `Linear` was constructed per matmul call (one
hipBLASLt handle created and destroyed ~500 times per pass). Hoisting it to a
Runner member is worth ~7 % of the pass — worth doing, but it was not the missing
time.

# M3.13 — where the decode's 127 ms/token actually go (ablation)

The per-phase event sums were unreliable (events are single objects, so every
recorded pair ended up pointing at the same two events). Ablation is robust:
`OMPH_SKIP_GEMV=1` and `OMPH_SKIP_STAGE=1` skip a phase (wrong results, valid
timing) and the delta is its cost.

| run (prefill + 20 decode steps, --gemv) | wall clock |
|---|---:|
| full | 10036 ms |
| without the fused GEMVs | 9063 ms |
| without stage+GEMM | 8984 ms |

So the fused GEMVs cost **973 ms / 20 steps = 48 ms per token**. The covered
weights are ~11.2 GiB, i.e. **~250 GB/s — essentially the measured ceiling**, and
that includes the lm head's 682 MiB.

**Conclusion: the GEMV path is already at the achievable decode bandwidth.** The
decode step is 127 ms/token, so ~79 ms is *glue*: the per-layer small kernels
(RMSNorm, residuals, casts, SwiGLU), the 5-launch-per-token delta rule, the
attention, and ~900 launches per step. The next decode work is not faster GEMVs
— it is PLAN §10.6 (fold norms and residuals into GEMV prologues/epilogues),
§10.2 (one fused delta-net decode kernel instead of five tiny launches) and then
HIP graphs (M4).

## Second ablation: the layer body

| run (prefill + 20 decode steps, --gemv) | wall clock |
|---|---:|
| full | 10017 ms |
| without the layer body (block + residual + FFN) | 7470 ms |
| without the fused GEMVs | 9041 ms |

The layer body costs 2547 ms = **127 ms per decode step — the entire step** — of
which 48 ms is the fused GEMVs. So **~79 ms per step is the body without its
matrix multiplies**: the attention/delta-net kernels, the per-layer norms,
residuals and casts, spread over roughly 600 launches per step. At ~130 us per
kernel that is not launch overhead; the kernels themselves are latency-bound.

The dominant piece is the delta rule as **five tiny launches per token per
layer** (48 layers x 5 = 240 per step, each on a 48-head grid with LDS-heavy
state access). That is exactly what PLAN §10.2 prescribes fusing into one kernel
per layer — and it is now the top decode item, ahead of HIP graphs.
