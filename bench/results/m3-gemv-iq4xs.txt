# M3.2 — fused IQ4_XS GEMV + repacking (2026-09-30)

Type IQ4_XS: 4-bit codes into the 16-entry non-linear codebook `kvalues_iq4nl`,
per-sub-block `d * (scale6 - 32)`. 2.81 GiB of the allocation, 96 tensors — the
second-largest type after IQ3_S.

Conditions: `omph-gemv-bench`, median of 5 runs, ROCm 7.2.4, gfx1200, desktop
idle (PLAN.md §17). Ceiling: 318.3 GB/s measured (`bench/results/m0-bandwidth.csv`).

## Summary (median of 5 runs)

| measurement | time | bytes read | effective bandwidth | vs ceiling |
|---|---:|---:|---:|---:|
| all 96 IQ4_XS tensors, one pass | **11.72 ms** | 2924.4 MiB | **261.6 GB/s** | **82.2 %** |
| single tensor `blk.63.ffn_up` (45.2 MiB) | 0.165 ms | 45.8 MiB | 291.5 GB/s | 91.6 % |
| *(reference: Q4_K `output.weight`, M3.1)* | 2.90 ms | 701.0 MiB | 253.2 GB/s | 79.6 % |

Repacking verified lossless for all 96 tensors (rebuild of the source block
stream compared byte for byte). Accuracy against the f16 dequant + hipBLASLt
path: max |d| 7e-4 (2.4e-4 relative), mean |d| 1e-4.

## Optimisation attempts (measured)

Final state: **261.6 GB/s = 82.2 % of the ceiling** over the whole type (169.1 before).

| change | result | kept? |
|---|---:|---|
| baseline | 169.1 GB/s (53.1 %) | — |
| activation staging in chunks of 256 sub-blocks (16 KiB LDS) | 186.0 GB/s (58.4 %) | yes |
| **outer product: 4 output rows per warp** (one activation value feeds four rows, four independent FMA chains) | **261.6 GB/s (82.2 %)** | **yes** |
| rows per warp = 2 | 183.1 GB/s (57.5 %) | no |
| rows per warp = 8 | 146.7 GB/s (46.1 %) | no |
| activation read as `__half2` | 80.8 GB/s (25.4 %) | no |
| activation read as `uint4` | 82.3 GB/s (25.9 %) | no |
| padded LDS stride (34 halves, coprime with the banks) | 126.0 GB/s (39.6 %) | no |
| *diagnostic:* codebook lookup replaced by an arithmetic placeholder | 201.9 GB/s (63.4 %) at baseline | n/a |

Reading of the evidence: the kernel was **instruction-issue/latency bound**, not
LDS-conflict bound — the padded layout (which removes the 16-way conflict) made
things *worse*, while amortising one activation load over four rows and adding FMA
independence made them 40 % better. The surviving ideas are the ones that reduce
instructions per weight, not the ones that change the access pattern.

| change | result | kept? |
|---|---:|---|
| baseline | 169.1 GB/s (53.1 %) | — |
| **activation staging in chunks of 256 sub-blocks** (16 KiB LDS) instead of the whole k | **186.0 GB/s (58.4 %)** | **yes** |
| activation read as `__half2` (16 LDS ops per 16 weight bytes instead of 32) | 80.8 GB/s (25.4 %) | no |
| activation read as `uint4` + chunked staging | 82.3 GB/s (25.9 %) | no |
| *diagnostic:* codebook lookup replaced by an arithmetic placeholder (wrong values, same loads) | 201.9 GB/s (63.4 %) | n/a |

The chunked staging is kept: with it, the k = 17408 tensors stage 16 KiB instead of
34 KiB of LDS, which lifts the workgroup-per-CU limit. It is worth +10 % over the
whole type.

Both attempts to read the activation with vector loads made things **2x worse**, and
the reason is not yet understood — 32 lanes stepping one 64-byte sub-block each means
the LDS addresses are 64 B apart, i.e. every lane lands on the same couple of banks
(16-way conflict), and a wider load apparently serialises harder instead of helping.
The obvious follow-up is a padded/transposed LDS layout for the activation
(sub-block stride 33 halves instead of 32) so that consecutive lanes hit consecutive
banks, and re-testing the vectorised reads on top of that.

## Why it is slower than Q4_K

The core loop is the same shape, but every value needs a **codebook lookup with
a divergent index**, which lands in LDS. Two measurements narrow it down:

- Factoring the per-sub-block scale out of the sum (`acc += dl * Σ table[c]·x`
  instead of `Σ (dl·table[c])·x`) and switching the LDS table from int8 to f32
  changed the result by 0.2 % (52.8 -> 53.0 %), so the kernel is **not ALU-bound**.
- The aggregate (2.9 GiB) and the single 45 MiB tensor agree within 2 %, so it
  is not L2 residency or launch overhead either.

That points at the LDS/bank behaviour of the 16-entry lookup (32 divergent
lookups per 16 bytes read). Follow-ups to try, in order:

1. Select the codebook entry with byte-permute instructions (`v_perm_b32` over
   four 32-bit registers holding the 16 int8 values) instead of an LDS gather.
2. Keep the codes' low/high nibbles in separate streams so each lane's 16-byte
   load covers one 32-value run of a *single* sub-block (better locality).

# M3.6 — profiling attempt: occupancy, and why the HW counters are empty

## Hardware performance counters: not available

`rocprofv3 --pmc ...` runs and produces a counter CSV, but every value is 0
(the dispatch rows are there, the values are not) — the counters need the AMD
perf permissions this box does not grant, so no counter-based analysis is
possible without a sysctl change. What the CSV *does* give for free is the
static per-kernel resource usage:

| kernel | VGPRs | LDS (dynamic) |
|---|---:|---:|
| `gemv_q4k` (Q4_K) | 128 | k x 2 B |
| `gemv_iq4` (IQ4_XS) | 120 | 16.4 KiB |
| `gemv_iq3` (IQ3_XXS) | 120 | 17.5 KiB |
| `gemv_iq3s` (IQ3_S) | 152 | 18.4 KiB |

## Occupancy (hipOccupancyMaxActiveBlocksPerMultiprocessor, 256 threads)

`OMPH_OCCUPANCY=1 omph-gemv-bench ...` reports workgroups per CU: q4k 6,
iq4 3, iq3xxs 3, iq3s 3 with the *maximum* chunk reserved. 

That exposed a real waste: the wrappers asked for the largest chunk even when
k is small enough to fit in one (k = 5120 needs 10 KiB, not 16.4). The dynamic
LDS size is now `min(n_sub, chunk) * 64 + tables`, which raises the occupancy
for the common shapes. Measured effect on the aggregates so far: neutral
(261.2 vs 261.6 GB/s for IQ4_XS) — the big-k tensors were already chunked,
and the small-k ones were not occupancy-limited.

## Where this leaves the optimisation work

The counter data is unavailable, but the A/B experiments already measured the
answer for IQ4_XS: removing bank conflicts (padded LDS) made things *worse*,
while removing instructions per weight (outer product over 4 rows) made them
40 % better. So the kernels are instruction/latency bound, not memory bound,
and the remaining levers are:

1. **Submission overhead** — the type aggregates lose 10-15 points on the
   small tensors (attn_k/attn_v are 2.7 MiB and run at 148 GB/s). HIP graphs
   are the fix, and they belong to M4.
2. **Small batch N = 1...5** — same weights, more tokens; the only lever that
   increases arithmetic intensity in decode (and it is what MTP verification
   needs).
3. **Wire the GEMVs into the runtime** — end-to-end decode numbers instead of
   per-tensor ones.

# M3.7 — fused GEMVs wired into the runtime (decode)

`--gemv` makes the runtime repack every tensor with a fused kernel at load and
use the GEMV for single-token steps; the rest falls back to the f16 dequant +
hipBLASLt path. Weights are read once and kept in one image (~11.4 GiB); the f16
fallback for repacked tensors re-stages the original bytes from the mmap.

## Decode (10-token prompt, 20 greedy steps timed)

| path | prefill | decode |
|---|---:|---:|
| f16 (milestone 2) | 2161 ms | **831 ms/token** (1.2 t/s) |
| **fused GEMV** | 8129 ms | **174 ms/token** (5.7 t/s) |

**4.8x faster decode, and the generated tokens are byte-identical to the f16
path** (198 760 3841 13477 37550 33075 888 279 15217 5388 13 198), which is also
the milestone-2 reference sequence.

Prefill got *slower* with `--gemv` (2161 -> 8129 ms): the f16 fallback for
repacked tensors stages the original quantized bytes from the mmap through the
host on every layer, ~1.6 GB per pass. Prefill speed is priority 3 and the M8
WMMA path replaces it; recorded rather than papered over.

## Where the remaining decode time goes

The covered 9.82 GiB should take ~39 ms at ~250 GB/s, so most of the 174 ms per
token is the **f16 fallback for the 1.46 GiB of uncovered types** (IQ2_S, Q6_K,
IQ2_XS/XXS, BF16/F32/IQ1_M = 14 % of the weights), which is read at 2 bytes per
weight instead of ~0.5 plus its dequant and staging. The next lever is therefore
not a faster kernel, it is **removing the fallback**: a GEMV for Q6_K and IQ2_S
covers most of it.

# M3.8 — fused Q6_K GEMV (0.32 GiB, but MTP-only)

| measurement | result |
|---|---:|
| all 8 Q6_K tensors (218.3 MiB) | **157.3 GB/s = 49.4 %** of the ceiling |
| accuracy vs the f16 dequant path | max \|d\| 6e-4 (**6.4e-5 relative** — the best of the five) |
| repack round-trip | byte-identical, source size (332.2 MiB) |
| rows per warp 2 / 4 / 8 | 142.9 / **157.3** / 79.5 GB/s |

The slowest kernel of the set. Each 128-weight group needs 96 quant bytes
extracted through two levels of shifts (16 `ql` words + 8 `qh` words held in
registers) plus a 4-quarter sub-accumulation, so it is heavier per value than
Q4_K/IQ4_XS and the register count shows it.

**Finding that matters more than the number: every Q6_K tensor in this model
lives in `blk.64.*`, the MTP block.** The normal decode path never touches them,
so this kernel is an M6 (MTP) enabler, not a decode win — and it does *not* help
the f16 fallback that dominates the current 174 ms/token.

That also corrects the previous estimate of the fallback: of the 1.46 GiB of
uncovered types, ~0.75 GiB is the token embedding (a row gather, not a GEMV) and
0.32 GiB is MTP. The fallback actually on the decode path is roughly 0.7 GiB
(6 % of the weights): IQ2_S outside the embedding, IQ2_XS/XXS and IQ1_M.

# M3.11 — the two questions: grid residency, and the cost of the sign

## (a) Does the grid's LDS residency matter?

No. Moving the IQ2_S grid (8 KiB) out of LDS into a const table (L1-resident,
freeing the LDS for occupancy) changed the kernel by 140.5 -> 139.6 GB/s, i.e.
nothing. So the kernel is not occupancy- or LDS-bound, and shrinking the grid's
footprint is not a lever.

## (b) Can the per-value sign select fold into the grid lookup?

The sign is *expensive* (removing it as a diagnostic — wrong results, valid
timing — gives 140.5 -> 189.1 GB/s, so it is worth ~26 % of the kernel), but it
does **not** fold away:

- it is a per-value mask (8 bits per 8-value group), not a per-group scalar, so
  it cannot go into the scale;
- folding it into the activation is impossible: the activation is shared by the
  four rows of a warp while each row has its own mask;
- the alternatives (pre-negated grid copies, `copysign`, ±1 tables, per-byte
  XOR masks) all cost at least the one op they would replace.

What *did* pay is the same class of win next to it: the byte extraction. The
compiler was emitting shift+mask+convert — three instructions per value — for
what the ISA does in one. `v_cvt_f32_ubyteN` is not exposed as a builtin for
gfx1200, so it goes through inline asm, built explicitly into float arrays (a
switch helper folded badly and cost 40 % everywhere).

| type | before | after |
|---|---:|---:|
| IQ2_S | 140.5 GB/s (44.1 %) | **233.6 GB/s (73.4 %)** |
| IQ2_XXS | 171.0 GB/s (53.7 %) | **231.2 GB/s (72.7 %)** |
| IQ2_XS | 166.1 GB/s (52.2 %) | **200.1 GB/s (62.9 %)** |
| IQ3_S | 219.5 GB/s (68.9 %) | 220.6 GB/s (69.3 %) |
| IQ3_XXS | 246.1 GB/s (77.3 %) | *reverted* — the array form cost 4 % there |

Accuracy is unchanged in every case (2.0-2.4e-4 relative).

End to end the decode stays at ~128 ms/token: those three types are only ~6 % of
the weights, so a 20-66 % kernel gain is worth ~4 ms. The value here is that the
slowest kernels are no longer an outlier — IQ2_XXS/S now sit with IQ4_XS and
IQ3_XXS — and that the same instruction replaces the extraction in any future
grid kernel.

# M3.12 — prefill phase breakdown (OMPH_TIMING=1)

10-token pass, f16 path, 2.0 s wall clock of which ~0.56 s is the one-time
weight upload over PCIe; the pass itself is ~1.45 s (~7 t/s).

| phase | time | share |
|---|---:|---:|
| dequant each layer's weights to f16 (`stage_w`) | 830 ms | 57 % |
| f16 GEMMs (hipBLASLt) | 339 ms | 23 % |
| attention / gated delta net kernels | 43 ms | 3 % |
| small ops, casts, launches (residual) | ~200 ms | 14 % |

Two conclusions for milestone 8:

- **80 % of the pass is the two things M8 replaces** (f16 materialization and
  small-M GEMMs), which is the quantitative version of the §4.2 argument.
- the block kernels are only 3 % *at T = 10* because the delta net is
  sequential today; they are exactly what grows with T, so the chunked form
  (§10.3) is what keeps a 512-token prompt from being delta-net bound.

Also fixed while measuring: `Linear` was constructed per matmul call (one
hipBLASLt handle created and destroyed ~500 times per pass). Hoisting it to a
Runner member is worth ~7 % of the pass — worth doing, but it was not the missing
time.

# M3.13 — where the decode's 127 ms/token actually go (ablation)

The per-phase event sums were unreliable (events are single objects, so every
recorded pair ended up pointing at the same two events). Ablation is robust:
`OMPH_SKIP_GEMV=1` and `OMPH_SKIP_STAGE=1` skip a phase (wrong results, valid
timing) and the delta is its cost.

| run (prefill + 20 decode steps, --gemv) | wall clock |
|---|---:|
| full | 10036 ms |
| without the fused GEMVs | 9063 ms |
| without stage+GEMM | 8984 ms |

So the fused GEMVs cost **973 ms / 20 steps = 48 ms per token**. The covered
weights are ~11.2 GiB, i.e. **~250 GB/s — essentially the measured ceiling**, and
that includes the lm head's 682 MiB.

**Conclusion: the GEMV path is already at the achievable decode bandwidth.** The
decode step is 127 ms/token, so ~79 ms is *glue*: the per-layer small kernels
(RMSNorm, residuals, casts, SwiGLU), the 5-launch-per-token delta rule, the
attention, and ~900 launches per step. The next decode work is not faster GEMVs
— it is PLAN §10.6 (fold norms and residuals into GEMV prologues/epilogues),
§10.2 (one fused delta-net decode kernel instead of five tiny launches) and then
HIP graphs (M4).

## Second ablation: the layer body

| run (prefill + 20 decode steps, --gemv) | wall clock |
|---|---:|
| full | 10017 ms |
| without the layer body (block + residual + FFN) | 7470 ms |
| without the fused GEMVs | 9041 ms |

The layer body costs 2547 ms = **127 ms per decode step — the entire step** — of
which 48 ms is the fused GEMVs. So **~79 ms per step is the body without its
matrix multiplies**: the attention/delta-net kernels, the per-layer norms,
residuals and casts, spread over roughly 600 launches per step. At ~130 us per
kernel that is not launch overhead; the kernels themselves are latency-bound.

The dominant piece is the delta rule as **five tiny launches per token per
layer** (48 layers x 5 = 240 per step, each on a 48-head grid with LDS-heavy
state access). That is exactly what PLAN §10.2 prescribes fusing into one kernel
per layer — and it is now the top decode item, ahead of HIP graphs.

# M3.14 — fused one-token delta rule: decode 127 -> 84 ms/token

PLAN §10.2's "one fused kernel per layer" for the sequential part: one launch per
token per layer does the decay, `sk = S^T k`, `d = (v - sk) * beta`,
`S += k (x) d` and `o = scale * S^T q`, with one workgroup per head (256 threads,
two per column) and the state touched twice instead of five times.

| path | before | after |
|---|---:|---:|
| fused GEMV decode | 127 ms/token | **84 ms/token** |
| f16 decode | 831 ms/token | 630 ms/token |
| f16 prefill (10 tokens) | 2145 ms | 1983 ms |

The f16 numbers move too because the prefill's per-token loop was five launches
as well.

Correctness: the greedy sequence is unchanged (198 760 3841 ...) and the logits
differ from the f16 path by max |d| 0.0104 with the same argmax — only the
summation order changed.

That is **9.9x the milestone-2 decode** (831 -> 84 ms/token), and the ablation
predicts the next step: of the 84 ms, ~48 is the fused GEMVs (already at the
bandwidth ceiling) and ~36 is the remaining glue — attention kernels, per-layer
norms, residuals, casts and the ~500 launches per step that HIP graphs (M4)
would collapse.

# M3.15 — stop staging the embedding per token: decode 84 -> 70 ms/token

The embedding is a row gather, not a matmul, but it was in the repacked set, so
`raw_bytes()` copied the whole 388 MiB table host->device on *every* token
(~19 ms at PCIe speed). Keeping its raw bytes in the image removes that.

| path | before | after |
|---|---:|---:|
| fused GEMV decode | 84 ms/token | **70 ms/token** |
| f16 decode | 630 ms/token | 630 ms/token (never staged) |

Greedy sequence unchanged. That is **11.9x the milestone-2 decode** (831 -> 70
ms/token), of which ~48 ms is the fused GEMVs at the bandwidth ceiling and ~22 ms
is glue (attention kernels, per-layer norms, residuals, casts, launches).

Same class of waste still applies to the prefill with `--gemv` (the f16 fallback
stages every repacked tensor, ~1.6 GB per pass); the fix there is the small-batch
GEMV, not more staging.

# M3.16 — flash attention: decode 70 -> 59 ms/token

The attention attribution (skip-the-attention ablation: 16 ms/step, ~1 ms per
layer at T = 1) pointed at the naive kernel, which recomputed each Q·K dot
**three times** (max, sum, weighted) and, worse, **per output dimension** — ~768x
redundant work at the tested shapes.

Replaced with a flash-style kernel (PLAN §10.4): one workgroup per (query token,
head), one thread per head dimension, each cache row's score computed once and
staged in LDS, the cache walked in blocks of hd rows with online softmax
rescaling. The old kernel is gone.

| path | before | after |
|---|---:|---:|
| fused GEMV decode | 70 ms/token | **59 ms/token** |
| f16 decode | 630 ms/token | 621 ms/token |

Tokens identical, logits within max |d| 0.0106 of the f16 path (summation order).

Also this round:
- the delta net's front end (conv + state shift + silu + split) is now one launch
  instead of four — logits bit-identical, no measurable time change, which is
  itself a finding: in that path it is not the launch count that costs.
- a prefill-only run with `--gemv` no longer repacks anything: 8100 -> 2100 ms.

**Decode is now 59 ms/token = 14.1x the milestone-2 f16 path.** Of that, ~48 ms
are the fused GEMVs at the bandwidth ceiling and ~11 ms is the remaining glue —
the attention's own GEMMs plus per-layer norms, casts and launches.

`check_gpu_decode.py --gemv --generate 3` (fused GEMV decode, flash attention,

- engine generated `[198, 760, 3841]`, NumPy reference `[198, 760, 3841]` —

## Where the 59 ms/token sits

The fused GEMVs cost 48 ms, which matches the weighted average of the per-type
efficiencies (Q4_K 92 %, IQ4_XS 82 %, IQ3_XXS 77 %, IQ3_S 69 %, IQ2_S 73 %,
IQ2_XS 63 %, Q2_K 66 % -> ~77 %) against the 318 GB/s ceiling. So the GEMV path
is at its *own* weighted ceiling: further decode gains have to come from the slow
types or from the ~11 ms of glue, not from the fast ones.

## Method note worth keeping

Two attribution mistakes cost real time in this milestone and both are recorded
here: event-based per-phase sums are meaningless when the same event objects are
re-recorded (every pair points at the last recording), and a Python simulation of
a kernel written *from the kernel* instead of from the spec will happily agree
with a bug. Ablation switches and spec-derived simulations are what worked.

# M3.18 — IQ3_S: the sign select is 46 % of the kernel

Diagnostic (sign select removed — wrong results, valid timing): **220.6 -> 321.6
GB/s**, i.e. +46 %, and that is the ceiling itself. So for IQ3_S the per-value
sign handling, not the grid lookup or the index assembly, is what keeps it at
69 %.

The compiler turns `if (mask & bit) v = -v;` into a compare plus a select per
value; the mask extraction adds another op or two. Every formulation that keeps
the sign per value costs about the same (a +/-1 table, `copysign`, a XOR against a
mask word all need the mask *and* a select), and the two that would remove it —
pre-negated grids (256x the LDS) or folding it into the scale (the mask varies
within a group while the scale does not) — do not work. IQ3_XXS (77 %) has the
same structure and the same ceiling.

Recorded as an open item with its measured upper bound: IQ3_S alone is 3.39 GiB
(30 % of the weights), so closing it would be worth ~3-4 ms of the decode's
59 ms/token if a cheap sign application can be found.

# M3.19 — the decode is GPU-bound; three fusion attempts were neutral

Measured with a fresh event pair around a single decode step (OMPH_TIMING=1):
**~65 ms of GPU time per step** against ~60 ms of wall clock — the events
themselves add a synchronise, so the honest reading is "GPU busy, not host
submission bound". HIP graphs therefore address less than assumed.

Three fusions were tried and all came out **neutral** (within noise):

| change | launches removed | decode |
|---|---:|---:|
| conv + state shift + silu + split in one kernel | 3 per delta layer (144/step) | 70 -> 71 ms |
| RMSNorm writing f16 (two per layer), SwiGLU + cast in one | ~3 per layer (192/step) | 59 -> 60 ms |

Both are kept: fewer launches, fewer passes over the activations, identical
results (logits bit-identical for the conv fusion, tokens identical throughout).
But they say the quiet part out loud: **the remaining glue is per-kernel latency
on dependency chains with tiny grids, not launch count** — which is why merging
three of ~1600 launches, or 192 of them, moves nothing.

## Where the 60 ms/token stands

- ~46 ms is the GEMVs, computing from their own measured per-type rates (Q4_K
  92 %, IQ4_XS 82 %, IQ3_XXS 77 %, IQ3_S 69 %, IQ2 63-73 %, Q2_K 66 %) against
  the 318.3 GB/s ceiling. That is the floor for this set of kernels.
- ~14 ms is everything else: the attention's own GEMMs, per-layer norms, casts,
  the delta rule, and the latency between dependent tiny kernels.

So the remaining decode levers are, in order: a cheaper sign application in
IQ3_S/IQ3_XXS (worth ~3-4 ms if one exists, see M3.18), and attack on the
per-kernel latency of the small-op chains — for which HIP stream capture is the
tool, with the caveat above that the win is smaller than the 22 ms estimate that
started this thread.

# M3.20 — investigation 1: a cheaper sign application

The sign costs ~46 % of IQ3_S (M3.18, upper bound by removal). Replacing the
per-value `if (mask & bit) v = -v;` with **masks built once per 8-value group and
a XOR on the float sign bit** helps where the register/instruction mix allows:

| type | select (before) | XOR (after) |
|---|---:|---:|
| IQ3_XXS | 246.0 GB/s (77.3 %) | **273.3 GB/s (85.8 %)** |
| IQ3_S | 220.7 GB/s (69.3 %) | **241.9 GB/s (76.0 %)** |
| IQ2_XS | ~200 GB/s | ~194-215 GB/s (noisy, small tensor) |
| IQ2_XXS | 227.2 GB/s (71.4 %) | 216.6 — **worse**, reverted |
| IQ2_S | 232.7 GB/s (73.1 %) | 208.4 — **worse**, reverted |

So the answer to "can the sign be made cheaper" is: **sometimes, and only by
measuring**. The two that lost have the same structure — the extra 8-entry mask
array pushed them over a register threshold. Kept: the three that measured faster.
Accuracy unchanged everywhere (2.0-2.7e-4).

Decode: 59 -> 58 ms/token (the win is concentrated in IQ3_XXS/IQ3_S, ~4.3 GiB).

# M3.21 — investigations 2 and 3

## 2. Per-kernel dispatch latency, measured with the dispatch trace

`rocprofv3 --kernel-trace` (counters do not work on this box; the trace does)
over prefill + 2 decode steps: 5585 dispatches, **1861 of them in a single decode
step**, which runs 78.7 ms of span with **91 % GPU busy**. So:

- the host is *not* the bottleneck (it was already indicated, now confirmed);
- a decode step is ~1861 kernels, and the non-GEMV ones (~1480) take ~17 us each
  on the GPU for trivial work — that is dispatch latency on a dependency chain,
  ~25 ms of the step;
- the GEMV dispatches (~380/step) account for ~46 ms.

The earlier fusion experiments removed 144 and 192 dispatches — under 20 % of the
small ones, which is why they measured as noise. **The lever that matches this
number is HIP stream capture**, not fusing a few percent more kernels: a graph
replaces ~1861 dispatches with one, and the GPU's own scheduler removes most of
that 17 us. This corrects the estimate in M3.19: the decode is GPU-busy, but a
large part of that "busy" *is* per-kernel dispatch overhead, which graphs do
address.

## 3. The small-batch GEMV is worth ~3.6x the prefill

Quantified, not yet implemented: with NT = 5 tokens per weight read, a 10-token
prefill reads the 12.02 GB of weights twice instead of the f16 path's
(materialize 54 GB + read it + read the quantized 12 GB). The prefill's measured
830 ms of staging + 339 ms of GEMM collapse to ~96 ms of GEMV, i.e. the pass goes
from ~1.45 s to ~0.4 s — **~3.6x the prefill** — and the same kernel is the
prerequisite for MTP verification (M6). It is the strongest remaining lever in
the project after the decode graphs.

# M3.22 — small-batch Q4_K: four tokens per weight read, 3.2x per token

The levers from M3.21, first one implemented. `gemv_q4k_b4` reads the weight bytes
once and uses them for four tokens (N = 1..5 from PLAN §10.1; four here), with the
four result vectors written token-major — i.e. straight into the (T, out) layout
the runtime already uses.

| version | ms per 4 tokens | ms/token | vs single-token |
|---|---:|---:|---:|
| single-token Q4_K | 2.344 | 2.344 | 1.0x |
| b4 with the activation staged in LDS (R=2) | 7.94 | 1.99 | 1.18x |
| b4 with LDS staging, R=4 | 5.60 | 1.40 | 1.67x |
| **b4 reading the activation from L1/L2 instead** | **2.903** | **0.73** | **3.2x** |

Accuracy: max |d| **0.000e+00** against four single-token GEMVs, at every step.

The intermediate results are the interesting part: staging the four activation
vectors in LDS cost *more* than the weight traffic it was meant to help — 40 KB
per workgroup against 82 KB of weights at R=4 — and dropping it turned a losing
kernel into a 3.2x one. The activation vector is 10 KB per token and read by every
row group, so L1/L2 already had it; the LDS copy was pure overhead.

Wired into the lm head for T > 1 (four tokens per read, the tail on the
single-token kernel): prefill 2104 -> 1967 ms, logits within 0.0092 of the chunked
f16 head (the same f16-weight rounding as everywhere else).

## The remaining port

Only Q4_K has the b4 form so far, so the prefill's other layers still dequantize
to f16. The measured per-tensor gain (3.2x) applied to the whole 11.2 GiB projects
the prefill's GEMV cost from ~1170 ms to ~144 ms, i.e. the pass from ~1.45 s to
~0.4 s (~3.5x, ~25 t/s). That is mechanical work: the same kernel shape for the
other six types.

# M3.23 — the small-batch path wired into the prefill

`matmul` now takes the b4 route for T > 1 on the types that have it (Q4_K, IQ3_S,
IQ4_XS — 68 % of the 11.2 GiB), four tokens per weight read with the tail on the
single-token kernel; the other types still stage f16.

Summed phase timers for a prefill + one token, the same binary:

| | stage_w | blocks | total |
|---|---:|---:|---:|
| f16 path | 843 ms | 0 ms | 843 ms |
| b4 path | 3 ms | 220 ms | **223 ms** |

620 ms off the prefill — 43 % of it — with two thirds of the weights ported. The
staging timer collapsing from 843 ms to 3 ms is the whole point: those weights are
no longer materialised in f16 and read back.

Correctness end to end: greedy tokens identical (`198 760 3841`), prefill logits
within 0.0087 (4.7e-04 relative) of the f16 path — the quantised-weight rounding
seen everywhere else — and the decode unchanged at 57 ms/token.

The remaining ~32 % of the weights (IQ3_XXS 1.93 GiB, then Q6_K, Q2_K and the
IQ2 family) are the same recipe: read the single-token kernel's inner loop, keep
its index arithmetic verbatim, and verify against four single-token GEMVs.

# M3.24 — IQ3_XXS ported, and what the b4 path is worth (measured by ablation)

IQ3_XXS joins the small-batch family (bit-identical to four single-token GEMVs,
0.026 ms/token vs 0.131 ms/token single — 5.0x). Wiring it in makes the coverage
5.0 GiB of ~11.2 GiB on this model (Q4_K, IQ3_S, IQ4_XS, IQ3_XXS).

With `OMPH_NO_B4` disabling the small-batch route, the same binary on the same
run gives a clean comparison (prefill + one token, summed phase timers):

| configuration | stage_w | blocks | total |
|---|---:|---:|---:|
| f16 (no repack) | 843 ms | 0 | 843 ms |
| `--gemv`, no b4 | 1575 ms | 0 | 1575 ms |
| `--gemv` with b4 | 2 ms | 297 ms | **298 ms** |

**5.3x faster than the gemv fallback, 2.8x faster than the plain f16 prefill**,

The earlier per-section phase numbers were not comparable between runs (timer

## Result 1: HIP graphs are worth ~1 ms, not 25 (negative, and that closes a line)

`omph-graph-probe` launches a chain of the same length as a decode step (1861
tiny dependent kernels) and replays the identical chain from a graph:

| | ms | us per kernel |
|---|---:|---:|
| launched one by one | 6.755 | 3.63 |
| replayed as a graph | 5.773 | 3.10 |
| saved | **0.982** | 0.54 |

A graph recovers 15 % of the per-kernel cost, i.e. **~1 ms of a 57 ms step**. The
schedule state I had inferred from the trace (91 % busy, 9 % gaps) does not imply
what I thought it did. This is the cheap experiment that pays for itself: the
device-side token/position refactor capture needs is not worth a 2 % win.

## Result 2: 96 BF16 GEMVs replace 119 tiny hipBLASLt GEMMs (-3.2 ms/step, -5.3 %)

`ssm_alpha`/`ssm_beta` are BF16 (type 30) and went through the f16 path: convert
to f16, then an M = 1 GEMM with 16x16 tiles — ~41 us per call for a 480 KB matrix.
`gemv_bf16` does the dot product directly (bf16 -> f32 is a shift).

The first version was *slower* than what it replaced: a warp-per-row grid gave
2 workgroups for 48 rows. One workgroup per row, k split across eight warps with
an LDS reduction, is the shape that works:

| | total for 40 decode steps |
|---|---:|
| OMPH_NO_BF16_GEMV=1 | 9578 ms |
| with gemv_bf16 | **9451 ms** |

3.2 ms per step, tokens identical (`198 760 3841`), 40 steps measured twice each.

# M3.26 — the two defects behind M4's criterion (issue #41)

Target: 55.7 ms/token (75 % of the 318.3 GB/s ceiling over 12.38 GiB).
Where the non-GEMV quarter of the step actually goes, from the kernel trace:

1. **`dequant_iq1_m` — 2 calls of 2.56 ms per step.** The IQ1_M `ffn_gate` is repacked
   (so it never took the f16 fast path) but has no GEMV kernel, so `stage_w` converted
   its 89M elements to f16 on *every* call. The f16 form is 178 MB, above the 64 MiB
   cache cap I first wrote — with the cap raised and the rule keyed on "types without a
   GEMV kernel", the runtime's own `stage_w` timer settles it:

   | | stage_w over 41 steps |
   |---|---:|
   | cache off | 77 ms |
   | cache on | **2 ms** |

   **1.83 ms per decode step**, tokens identical.
2. **`rms_norm_f16` — 165 calls at 15.5 us.** The decode calls it with one row, so it is
   one workgroup on a reduction path: eight barriers of shared-memory tree. Shuffles plus
   two barriers measure 14.06 us — better, but the reduction was not the dominant cost:
   the f32 sibling with the identical structure costs 2.95 us for the same work, so ~11 us
   per call is still unexplained. Kept (it measures better and has six fewer barriers),
   not solved.

Decode: 57 - 1.83 = **~55.2 ms/token = 240.7 GB/s = 75.6 % of the ceiling.**

# M5 prerequisites — long-context runs were dying on two unrelated things

Before touching the KV, the long-context path had to run at all:

- **The logits buffer.** `--last-logits` computes only the final token's row: the
  full (T, 248320) f32 buffer is 2 GB at 2k and 33 GB at 32k, so every long-context
  run was hitting `out of VRAM` on the logits, not on the model. The last-only row
  uses the single-token GEMV on the final activation (max |d| 6.8e-3 against the
  four-token b4 head on the same row — a different summation order, not an error).
- **The f16 cache** added in M4 threw when `hipMalloc` failed, which turns a
  long-context run that is merely tight on VRAM into a hard failure. It now falls
  back to the per-call staging buffer: caching is an optimization, never a reason
  to fail.
- Also fixed: the summary print walked `toks.size()` logit rows regardless of how
  many exist.

With those, the measured state of the f32 KV (16 attention layers, 4 KV heads,
head_dim 256 → 128 KB per token, 4.3 GB at 32k):

| context | result |
|---|---|
| 512 | runs; decode step 59.6 ms against 55.2 ms at short context — the KV read |
| 2048 | `error: ffn failed` — the f16 fallback stages a whole tensor into a scratch that no longer fits |
| 8192 | `error: out of VRAM` |

That is the milestone's case: with K Q8 + V Q4 the same 32k costs 0.8 GB.

# M5 — quantized KV: K Q8, V Q4, Hadamard rotation

Storage: 32-element blocks along head_dim (8 per head), scales in a separate f16
stream. Per head per token: K 272 B, V 144 B, against 1024 B each in f32.

| | 512 tokens | 32k |
|---|---:|---:|
| f32 KV | 67.1 MB | 4.29 GB |
| K Q8 + V Q4 | **13.6 MB** | **0.87 GB** |

**4.92x smaller**, and the reason the 16 GB card can hold a long context at all.

Quantization quality, measured on the host from the writer's own output:

| | error (max abs) | source |max| |
|---|---:|---:|
| K Q8 | 0.0142 | 3.295 |
| V Q4, unrotated | 0.1264 | 1.772 |
| V Q4, rotated | **0.0642** | 0.71 |

The V rotation is what makes Q4 usable: without it the block scales ranged
0.088-0.253 (outlier-dominated, the 1.77 against block-mates near 0.2); with it
they are uniform at 0.10-0.14.

Correctness: greedy tokens identical to the f32-KV run at the short prompt
(`198 760 3841`); KL(f32 || q8q4) = 0.139 nats at 10 tokens and **0.0837 nats at
512**, with the argmax preserved at 10 tokens and the top-10 probability mass
within 0.4 %. On the random 512-token prompt the argmax does diverge — that
prompt is out of distribution by construction, and the FP16 windows of §13.4 (not
implemented yet) are the intended remedy.

Speed: no change at 512 tokens (KV reads are 67 MB against 12.4 GiB of weights
per step — 0.5 %). At 32k the f32 KV is 4.3 GB of the step's traffic and the
quantized one 0.87 GB, so the win is there, but measuring it needs a 32k prefill,
which the f16 fallback's staging currently cannot do.

Two bugs worth recording, both found by dumping the writer's output rather than
reasoning about it: the block amax was reduced over 8 lanes while the Q4 writers
are 16 (`vmax` was 0 for half of them, storing zeros), and the KV cache stride
used the model layer index instead of the attention-layer index — the pointers
printed 175104 into a 147456-byte buffer.

# M5 validation — what works, and what the long context is actually blocked by

Unblocked while validating: the prefill's f16 fallback stages a whole weight
tensor, which at 2048 tokens no longer fit the scratch (`error: ffn failed`). For
the types that have a single-token kernel but no small-batch form, `matmul` now
runs one GEMV per token instead — no staging at all. 2048 tokens now runs (it did
not before); 8192 still does not, and not for the KV's sake:

| context | f32 KV | q8q4 KV |
|---|---|---|
| 2048 | runs | runs |
| 8192 | out of VRAM | **out of VRAM** |

At 8192 the activations alone are ~3 GB — `tmp_logits_` is T-scaled at 1.07 GB and
`ffn1_`/`ffn2_` at 570 MB each — against 12.4 GiB of weights. The KV quantization
saves 0.84 GB there and it does not matter yet: the prefill has to be chunked
before any 32k number means anything.

KL against the f32 KV, measured at the lengths that run:

| context | KL | argmax | note |
|---|---:|---|---|
| 10 (real prompt) | 0.139 | preserved | the golden prompt, greedy tokens identical |
| 512 | 0.0837 | diverges | random prompt |
| 2048 | 0.164 | diverges | random prompt |

The 512/2048 rows are pessimistic by construction: a random prompt gives the model
a nearly flat distribution (top-10 mass 0.007), so the KL is measuring noise on
the tails rather than a change in what the model believes. The real-prompt number
to quote is the 10-token one, and the honest statement is that the long-context
validation is still open.

# M5 — chunked prefill: 8192 tokens now runs at all

The activation buffers were sized by the whole prompt, so at 8192 they cost ~3 GB
(tmp_logits_ 1.07 GB, ffn1_/ffn2_ 570 MB each) on top of 12.4 GiB of weights and
the run died. `--last-logits` did not help: those buffers are allocated in the
constructor regardless.

The prefill now runs in chunks of 512 (activations by chunk, KV by the whole
sequence):

| context | before | after |
|---|---|---|
| 512 | runs | runs |
| 2048 | `error: ffn failed` | runs |
| 8192 | out of VRAM | **runs** |
| 32768 | out of VRAM | out of VRAM |

Two things 32768 is still short of, both identified rather than guessed:

1. **The f32 KV is still allocated alongside the quantized one** — 4.3 GB wasted
   in that mode. Skipping it looked like a two-line change and regressed the
   working 8192 case (the attention plumbing holds pointers into a cache that no
   longer exists), so it was reverted and is recorded here rather than half-done.
2. **The quantized attention dequantizes per (query, position) pair** — every one
   of the 256 query threads converts the same key from bytes, a 256x redundancy.
   That is why the quantized KV is *slower* at long context instead of faster:

   | 8192 tokens | step |
   |---|---:|
   | f32 KV | 79.5 ms |
   | K Q8 + V Q4 | 104.6 ms |

   At that length the KV reads are ~4 % of the step, so the bandwidth saved is
   ~3 ms against ~25 ms of extra conversions. The fix is the LDS-tiled form of
   PLAN §8.3 (dequantize each key block once per workgroup, reuse across the query
   positions) or the int8 dot of §13.8 — not more window tuning.
