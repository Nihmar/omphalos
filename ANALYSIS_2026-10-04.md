# Engine code review — inference, numerics, and the code around them

Date: 2026-10-04. Engine: `main` at `4e4ba46` (#311, the prefill progress line) plus the
penalties of #298. Reviewer: the coding agent, reading the sources, not the benchmarks.
Scope: everything that computes, i.e. `model/` (the forward pass, the runner, the
generator), `kernels/` (attention, GDN, GEMV, GEMM, dequant, elementwise), `runtime/`
(dispatch, matmul, allocations) and `format/repack.cc` (the layout side of correct
inference). The server, the tokenizer and the chat template were reviewed in the #284–#308
work and are only mentioned where they touch inference.

Method: read the code, reason about the invariants, and separate three kinds of statement —
**verified correct by reading** (with the argument), **confirmed defect**, and **needs a
test** (a suspicion the current checks cannot settle). The repository already validates the
happy paths densely (golden dumps per layer, KL against llama.cpp, greedy identity of
speculation, bit-exact repacking), so this review deliberately spends its effort on the
paths those checks do *not* reach and on the assumptions they cannot see.

Nothing I found contradicts the repository's own measurements: the paths the golden dumps
and the KL checks cover are, as far as I can tell by reading, correct. The findings above
are on the edges — inputs the checks do not use, modes they do not run, and small
deviations from the documented sampler semantics.

## 1. Correctness

### 1.1 `read_hparams` checks less than the kernels assume — low (corrected)

**Correction (2026-10-04, while fixing this in #315).** The first version of this finding
said a foreign model "loads and produces plausible nonsense". That was wrong: every kernel
wrapper validates the shapes *it* hard-codes before launching — `attention_gqa` rejects
`nh / nkv != kGqaGroup || nh % nkv != 0 || hd != kGqaHd` (`attn.hip:1296`) and `attn_prep` rejects
`hd != kPrepHd` (`attn.hip:192`); the delta-net wrapper rejects mismatched dims and the conv
window
(`gdn.hip:1140-1150`) — so the result is a failed layer, not a wrong one. What is left of the
finding is the *moment* and the *message*: the failure comes after the weights have been read
(11 GiB) and says "attention failed", which does not tell anyone that the model itself is the
problem. That is what #315 fixed: the constants moved to `kernels/shapes.hh`, shared with the
loader, which now refuses at load with the field and its values.

`hparams.cc:80-85` rejects a model whose `head_dim != 256`, whose `n_head` is not a multiple
of `n_head_kv`, whose `ssm_s != 128`, whose `ssm_inner`/`ssm_n_vh`/`ssm_n_kh` do not divide,
or whose head does not match the vocabulary. What the kernels additionally assume:

- `kernels/attn.hip:208`: `constexpr int kGqaGroup = 6;  // query heads per KV head (24 / 4):
  fixed for this model` — checked by `attention_gqa`, not by the loader (now checked by both).
- `kernels/attn.hip:10` (`kPrepHd = 256`), `kernels/gdn.hip:35` (`kDeltaS = 128`),
  `kernels/gemv.hip`'s tile constants and `kernels/gemm.hip`'s `k % 256 == 0` each encode
  `head_dim`, the state size, `n_embd` and `n_ff` of *this* model. The GEMM path checks its
  own preconditions and falls back (`gemm.hip:520-526`); the others reject the call.
- `ssm_conv_k` is checked by the conv wrapper ("conv_k (checked at launch)") but only at the
  first delta-net layer; the loader now refuses it too.

The engine is deliberately single-model (`PLAN.md`), so this was never a generality request:
it was about failing loudly *and early* — and, as the correction notes, about a failure that
names the field rather than one that looks like an engine bug.

### 1.2 top-p is normalised before min-p removes mass — low

`generator.cc:445-467`:

```cpp
double sum = 0.0;
for (const auto & c : cand) sum += std::exp((double) c.first);   // all top-k candidates
if (s.min_p > 0.0f) { cand.erase(remove_if(c.first < log(min_p))); }
if (s.top_p < 1.0f) { ... acc += exp(cand[sorted].first) / sum; ... }
```

`sum` includes the mass min-p is about to remove, so the cumulative mass `acc` grows more
slowly than the probabilities the sampler actually draws from and the top-p loop keeps more
candidates than `top_p` asks for — the two knobs do not compose the way the comment above
`distribution` ("temperature, then top-k, min-p and top-p over the tokens within e^-30 of
the best") and llama.cpp's chain say. With `min_p = 0.05` and `top_p = 0.95` the kept set is
measurably wider than intended.

Fix: renormalise after min-p (`sum` computed after the erase), or follow llama.cpp's order
(min-p after top-p). Either is a two-line change; it deserves a unit test on a synthetic
row, because no current check exercises the sampler chain's composition — `check_gpu_decode`
compares tokens with the reference sampler disabled, and the KL checks use greedy.

### 1.3 No finiteness check anywhere — low, but cheap insurance

Neither `logits` nor the KV/state buffers are ever tested for NaN/Inf. A NaN reaching the
sampler is especially unpleasant because the two argmax paths disagree about NaN
(`argmax_key` in `elementwise.hip:171-176` orders the raw bit patterns, so a positive NaN
wins; `std::max_element` keeps the first element): the same corruption produces different
tokens on the greedy device path and on the host path, which is exactly the kind of
inconsistency that is hard to see.

A validation-only switch (`OMPH_CHECK_FINITE`, one reduction over the logits row, ~0.1 ms
per step) would turn "the model went strange" into "the state at position N is not finite",
and it can be run alongside the golden checks.

## 2. Performance

### 2.1 `OMPH_KV_HOST` re-uploads the whole prefix on every call — medium (measured, corrected)

`layers.cc:311-318` copies the layer's whole prefix [0, pos0 + T) from the pinned host cache
into the staging buffer before every attention, per layer, per call. The new rows of a call
are T × 8 KiB, the upload is (pos0 + T) × 8 KiB: at 2.6k tokens, 16 layers × 2.6k × 8 KiB ≈
333 MB per step.

**Measured (2026-10-04, Qwen3.8-27B, 2600-token prompt, 4 decode steps, same session):**
`step gpu` 55.0 ms in the host mode against 42.4 ms with `OMPH_KV_F32` (the same exact f32
cache in VRAM, whose logits are bit-identical to the host mode's — verified with `cmp`) — so
~12.6 ms of the step is PCIe, and the cost grows linearly with the context (at 32k it is
twelve times larger, ~150 ms against ~45 ms of GPU). A chunked *prefill* is worse: each
chunk re-uploads the whole prefix for each layer, so the total is quadratic in the number of
chunks.

**Correction (attempted and reverted in #315).** The obvious fix — track how many rows of
the staging buffer already hold the layer's data and append only the new ones — is **wrong**:
the staging buffer is *shared* by the 16 attention layers, so the rows a previous layer
uploaded are that layer's K/V, not this one's. A per-layer row counter cannot detect it; the
effect is reading another layer's keys, which the bit check against `OMPH_KV_F32` caught
immediately (the first byte differed). What would work, in increasing cost:

1. **Per-layer staging buffers** — a full copy per layer: exact, but `n_layer × context ×
   8 KiB` of VRAM (1.1 GB at 8k, 4.3 GB at 32k), so it only fits up to roughly 16k — the
   opposite of where this mode is used.
2. **A key offset in `attention_gqa`** — stage the keys in pieces and accumulate the splits
   into the work buffer (the kernel already splits over key ranges and merges): the upload
   becomes piecewise and each piece is read once. A real feature, worth an issue of its own.
3. **Overlapping the upload with compute** (the side-stream machinery of #71): hides part of
   the cost, changes nothing about the traffic.
4. **Not using the mode when it fits**: `OMPH_KV_F32` is bit-identical, exact and staged by
   hardware; the host mode earns its cost only when the f32 cache does not fit in VRAM.

Until one of those lands, the mode's cost is what it is, and the comment in `layers.cc` says
so (so the wrong fix is not attempted again).

### 2.2 The MTP KV fill computes the Q projection for nothing — low

`layers.cc:59-61` says it: with `kv_only` the Q GEMV is skipped but `attn_prep` still runs
its `nh` query blocks over whatever `fused_` holds ("nobody reads their output"). The grid is
`(tokens, nh + 2*nkv)` = `(T, 32)`, of which 24 of 32 blocks are wasted. An `AttnPrep::skip_q`
flag (or simply not launching those blocks: the role dimension is the launch geometry, so a
`q_roles` count) removes ~¾ of the wasted work. The MTP fill is documented as +1.1–1.5 % of a
prefill, so the saving is small in absolute terms — but it is free.

### 2.3 `apply_penalties` copies and sorts per row — low

`generator.cc:395-410` builds a `std::vector<int32_t>` of the last `penalty_last_n` tokens
and sorts it, once per sampled row. In a 16-token verification that is 16 sorts of ≤1024
elements per step (~0.3 ms of a ~25 ms step, ~1 %), and it grows with the window that #298
showed to be necessary (1024). The counts only change by the drafts accepted between rows:
build the histogram once per step and add the few new tokens, or keep a small open-addressed
counter (`int32_t -> uint16_t`) instead of sorting.

### 2.4 The head paths are tuned for Q4_K — low (only if the head is re-quantized)

`forward.cc:294-300` (the verification argmax) and `forward.cc:327-355` (the batched head)
both require `head_.gemv->type == 12` (Q4_K). `head_chunked` (`forward.cc:398-433`) is
correct for any type but dequantizes `min(n_vocab, 32768) × n_embd` to f16 *per call* —
320 MiB of staging traffic per vocabulary chunk, 2.5 GB per full head pass. For this model
the head is Q4_K, so this never runs; a re-quantized head (Q6_K, Q8_0) would silently make
the head the prefill bottleneck. Worth a note in the code or a counter, not a change.

## 3. Numerical conventions worth writing down

These are not defects; they are the parts of the calculation a future reader (or a future
quantization change) must know, and they are only in the code today.

- **The V/K4 quantizer is asymmetric in scale**: `attn.hip:160-176` uses `vsc = amax / 7`
  with the 4-bit code stored as `q ∈ [0, 15]` unpacked as `q - 8`, i.e. levels
  `[-8·amax/7, +amax]`. llama.cpp's `q4_0` uses `d = -amax/8` (`[-amax, +7·amax/8]`). The
  engine's choice covers the observed maximum exactly and overshoots the negative end; it is
  validated against the KL budget (K Q8: `amax/127`, symmetric), so it is a *choice*, not a
  bug — but it is the kind of thing that must be noted when the budget is re-measured.
- **KV scales are f16** (`__half` scales, `attn.hip:155-158`), so a scale carries ~5·10⁻⁴
  relative error on top of the 8-bit or 4-bit levels. That is under the measured KL, but it
  is part of the error budget, not free.
- **The prefill and decode attentions read the FP16 window differently**: per query for
  ≤ 16 tokens (`attn.hip:1335`, `per_query`) and once per chunk ending at `seq` otherwise.
  The former is what makes a verification row bit-identical to a decode step (#161); the
  latter is a *different* arithmetic for the same keys. Correct as designed, invisible in
  the code comments unless one reads both.
- **`prefill_ms` includes the checkpoint save/restore** (`generator.cc`: `t0` is taken before
  `save_snapshot`/`resume`), so the prefill t/s printed in the log dips whenever a
  conversation is saved or restored (~150 ms per cut, #158). The field name and the log line
  say "prefill", which is what a reader would attribute to the GPU.
- **The WY prefill delta rule is an approximation of the exact recurrence** (#240, KL
  0.0002–0.0005): documented, and verifications always use the exact form — worth keeping in
  the same list as the KV quantisation when the next quality measurement happens.

## 4. Verified correct (with the argument)

This is the part of a review that matters as much as the findings: things that look wrong
but are not, so the next reader does not "fix" them.

- **The FP16 ring's `+15` slots** (`attn.hh:24`, `attn.hip:1335`). A chunk of `T ≤ 16` tokens
  uses each query's own window (`w_lo + t`) and needs the union
  `[q₀ - 127, q₀ + T - 1)` — `window + T - 1 = 142` positions for `T = 16`, against 143 slots;
  writing the 16 new positions evicts exactly `[q₀ - 143, q₀ - 128]`, all of them outside
  the union. For `T = 17` the code correctly stops using the per-query path
  (`tokens <= kKvRingExtra + 1`), so the ring can never be one slot short. (I first thought
  this was an off-by-one; the effective window is `window - 1` keys, and that is what closes
  it.)
- **The Hadamard rotation and the merge's un-rotation** (`attn.hip:79-101` forward,
  `325-355`/`867-900` read): the transform is orthonormal (`H/16`), so `(Hq)·(Hk) = q·k` (the
  scores are untouched) and `Σ wᵢHvᵢ = H(Σ wᵢvᵢ)` — the un-rotation may happen once, after
  the accumulation, which is what the merge does, and only for the quantised cache
  (`v_rotated`). The gate is elementwise in the *unrotated* head space and is applied after,
  which is also right.
- **The argmax key packing and its tie-break** (`elementwise.hip:171-176`): the monotone
  float→u32 map plus `0xffffffff - i` in the low half makes the *lowest* index win ties, so
  the device argmax agrees with `std::max_element` — the property `#161`/`#102` rely on.
  (Except for NaN, see 1.3.)
- **Speculative commit/rollback** (`runner.cc:1069-1180`): `commit(accepted)` swaps the
  alternate states only when every draft was kept, otherwise replays the kept prefix from the
  recorded rank-1 factors and restores the ring slots of the rejected positions; the
  EOG/drop-last-token convention of the speculative path matches the plain path's (the last
  emitted token is never fed into the cache). `OMPH_SPEC_CHECK` verifies both.
- **The penalty window** (`generator.cc:395-410`): `window = penalty_last_n - n_extra` and
  `extra = batch[0..a]` make row `a` of a verification see exactly the same `penalty_last_n`
  tokens a plain decode step would — including the drafts accepted so far.
- **KV indices and layouts** (`layers.cc:249-258`, `attn.hip:231-300`): the K Q8 row stride
  (1 byte/dim), the Q4 K/V byte/nibble packing (byte `j` = dims `j` and `j + 16`), the
  per-32-block scale index and the separate per-layer offsets for the mixed K4/K8 cache all
  agree between writer (`attn_prep`) and readers (decode, prefill, ring).
- **The GDN step's math** (`gdn.hip:38-200`): SiLU via `x/(1+e^{-x})` (no overflow either
  way), L2 norm as `y·(1/√s)·(1/√(mean + eps/s))` (matching FLA's normalisation), gates from
  BF16 rows dotted in f32, `decay = exp(softplus(a + dt_bias)·A)` with the stable softplus
  `log1p(e^{-|x|}) + max(x, 0)`. The golden-dump checks pin the result.
- **The dispatch fallbacks** (`dispatch.cc:90-224`): every specialised path (NT GEMVs,
  grouped launches, fused GEMM, SwiGLU epilogue) returns `false` *before* issuing work when
  it does not apply, and the caller falls through to the generic one; the ablations that
  intentionally produce wrong results are all behind `OMPH_*` names.

## 5. Validation gaps (each is a test I would write)

1. **Verifications of 9–16 tokens across the ring's window edge** with `OMPH_KV_K4=1` and
   `OMPH_KV_WINDOW=0`: the `per_query` path plus the K4-Q8 fallback *inside* a block is the
   most intricate branch in `attn.hip` and the checks use ≤ 8 tokens (the bit-identity
   witnesses of #161 are 4-token and 8-token verifications).
2. **The sampler chain's composition** (1.2): a unit test on a synthetic logits row with
   `min_p` and `top_p` both set, asserting the kept mass and the set, plus the penalties'
   interaction with the drafts (already covered by `check_spec_sampling.py` for the
   distribution, not for the truncations).
3. **`OMPH_KV_HOST` at ≥ 32k** (2.1): the mode is used for long-context validation; a
   timing check would keep its cost visible (`bench/`), and the fix above makes it cheap.
4. **A neighbouring model in the same family** (1.1, done in #315): a GGUF with, say, 4 KV
   heads and 32 query heads, asserting a clear refusal at load. A cheap fixture, no GPU
   weights needed — `engine/tests/test_hparams.cc` builds one per shape.
5. **The head with a non-Q4_K quantization** (2.4): a Q6_K head built by hand (or a
   synthetic one) through `head_chunked` against the reference, to pin the path that must
   stay correct even if it is slow.
6. **Multi-chunk prompts with an image at a chunk boundary** (`generator.cc:feed`'s
   `mpos.assign(p.mpos.begin() + 3*off, ...)`): the only place image positions cross a chunk
   boundary; `check_vision.py` uses one short prompt.

## 6. Ranked recommendations

| priority | change | effort | gain |
|---|---|---|---|
| 1 | the `min_p`/`top_p` normalisation fix + the unit test (1.2) | hours | correct sampler semantics; today the two knobs fight |
| 2 | `read_hparams`'s hard-coded-shape checks (1.1, corrected) | hours | a foreign model is refused at load, naming the field, instead of failing on its first layer with "attention failed" |
| 3 | `OMPH_KV_HOST`'s staging traffic (2.1, corrected): a key offset in `attention_gqa` and piecewise staging, or per-layer buffers where they fit | a day+ | removes ~12.6 ms of PCIe per step at 2.6k (≈150 ms at 32k) from the long-context reference runs |
| 4 | `OMPH_CHECK_FINITE` for validation runs (1.3) | hours | corruption is localised instead of debated |
| 5 | the verification 9–16 / K4 / window test (5.1) | a day | the least covered branch of the attention kernel gets a witness |
| 6 | a startup banner for the ablation switches (`OMPH_SKIP_*`, `OMPH_TEST_*`) | minutes | a stray `OMPH_SKIP_FFN=1` in a shell stops looking like a model bug |
| 7 | `apply_penalties` once per step (2.3) | hours | ~1 % of the sampled step at the window #298 needs |
| 8 | the `kv_only` Q-block waste (2.2) | hours | a small, free slice of the MTP fill |
| 9 | a warning when a repeat penalty is set with the default 64-token window | minutes | the measurement of #298 says a short window barely bites; the server currently accepts it silently |

Two knobs are worth an experiment rather than a change, both about long-context quality
(this user's main worry): the **FP16 window size** (`OMPH_KV_WINDOW`, 128 today — the ring
costs ~26 B/token of VRAM, so 256 or 512 are nearly free) and a **middle KV option**
(K Q8 + V Q8, or f16 KV) as a third point between the default and the f32 references.

## 7. What this review does not cover

- The GEMV/GEMM kernels' per-type index arithmetic (`gemv.hip`, `quant_decode.hh`,
  `iq_tables.hh`, ~4400 lines): the repository validates these bit-exactly against the NumPy
  decoders for every type the model uses (`validate_gpu_dequant.py`, `check_gpu_linear.py`,
  `gemv-bench --all-of-type`), which is stronger evidence than a reading, and the types not in
  the model are refused by `gemv_one`'s switch.
- The vision encoder (`vision/encoder.cc`, llama.cpp's mtmd on the CPU) and the HTTP layer.
- The performance claims themselves: I read the code around them and did not re-measure.
